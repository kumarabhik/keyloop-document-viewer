# AGENTS.md — Operating Manual for AI Coding Agents

This file tells any AI coding agent (Claude Code, Copilot, Gemini CLI, OpenCode, Kiro, …) how to work on this repository. Humans should read it too.

**Project:** Unified Document Viewer — Keyloop technical assessment, Scenario D. One VIN search → parallel calls to a Sales and a Service system → one merged document list with the source on every document.

---

## 0. The one rule above all others

> **Before writing any code, read the project Markdown files. They are the source of truth for progress, design and past decisions. After working, update them.**

Chat history is lost between sessions. These files are not. If something is not written in them, the next agent will not know it.

---

## 1. Source-of-truth files

| File | Purpose | When to read | When to write |
|---|---|---|---|
| [AGENTS.md](AGENTS.md) | How to work (this file) | Every session, first | Only when the working process changes (ask the human) |
| [ROADMAP.md](ROADMAP.md) | What to do next and what is done (`[ ]` / `[~]` / `[x]`) | Every session, second | Start and end of every task; end of every session |

**If two files disagree:** SYSTEMS.md (latest decision) > DESIGN.md > ROADMAP.md > code comments. Fix the stale file in the same session and say so in your summary.

## 2. Session start protocol

Do these steps in order, every time, before editing files:

1. Read this file.
2. Read **ROADMAP.md** → find *Current Focus*, any `[~]` task, and the last *Session Log* entry.
3. Read **SYSTEMS.md** → all decisions, the **Invariants** list, and recent errors.
4. Read the **DESIGN.md** sections that your task touches.
5. Run `dotnet build` and `dotnet test` (§7) to confirm the starting state. If it is red, fixing it is your first task; log the cause as an E- entry.
6. State your plan to the human in 3–6 lines: which task ID, which files, how you will verify it.

**Resuming a `[~]` task:** read its acceptance criteria, check what already exists in the code, finish it before starting anything else.

## 3. Task workflow

1. **Pick** the first unchecked task in the current day of ROADMAP.md (respect dependencies). Do not skip ahead without the human's agreement.
2. **Mark it `[~]`** in ROADMAP.md before writing code.
3. **Write or update tests first** for the behaviour described in the acceptance criteria where practical.
4. **Implement** the smallest change that satisfies the criteria. Stay inside the task's scope.
5. **Verify:** run lint, type-check and tests. Run the app or a cURL check when the task touches runtime behaviour. Read your own diff.
6. **Mark it `[x]`** only when **every** acceptance criterion is met and tests pass. If you stop early, leave it `[~]` and write exactly what remains in the Session Log.
7. **Record** decisions, errors and AI corrections in SYSTEMS.md (see §5).
8. **Commit** (only when the human has asked for commits) with a message like `D2.4: aggregation service with stale fallback (D-003, D-006)`.

### Definition of Done

- [ ] All acceptance criteria in ROADMAP.md are met.
- [ ] New logic has tests; the full suite is green.
- [ ] `dotnet build` passes with zero warnings (warnings are errors) and `dotnet format --verify-no-changes` is clean.
- [ ] No invariant in SYSTEMS.md §6 is broken.
- [ ] API changes are reflected in DESIGN.md §7 and `docs/openapi.json`.
- [ ] ROADMAP.md and SYSTEMS.md are updated.

## 4. Architecture rules (do not violate)

These are short versions. The reasoning is in SYSTEMS.md.

1. **Layering (enforced by project references):** `Api → Application → Domain` and `Infrastructure → Application → Domain`. `DocViewer.Domain` is pure: no I/O, no ASP.NET/EF/HTTP packages, no `DateTime.Now`/`UtcNow`. `DocViewer.Application` owns the interfaces (ports); Infrastructure implements them.
2. **Source quirks stay in adapters.** Field names like `docType`, `record_no`, and the `dd/MM/yyyy` format appear only in `DocViewer.Infrastructure/Sources/` and `mocks/`.
3. **Adapters never throw to the aggregator.** They catch pipeline/HTTP/JSON failures and return a `SourceResult`. An exception escaping `Task.WhenAll` is a bug. (Always let `OperationCanceledException` from the *caller's* token propagate.)
4. **Partial is data, not an error.** One source down ⇒ HTTP 200 with `partial: true`.
5. **Time is injected.** Use `TimeProvider` (never `DateTime.Now`, `DateTimeOffset.UtcNow`, `Stopwatch.StartNew` in business code); tests use `FakeTimeProvider`.
6. **Budgets are fixed by D-005 / D-014.** Do not add retries, change timeouts, or switch to `AddStandardResilienceHandler` without a new decision entry.
7. **Never cache partial responses** (D-006).
8. **VIN privacy** (D-011): log only `Vin.Masked`; never put a VIN in a metric tag; hash it before storing.
9. **Configuration through options classes** (`IOptions<T>` with validation on start). No hard-coded URLs, ports, secrets or TTLs elsewhere.
10. **Infra failures degrade, never fail.** Redis or Postgres errors are logged and counted; the search continues.
11. **Async all the way.** No `.Result`, `.Wait()` or `async void`; pass `CancellationToken` through every async method.

## 5. What to record in SYSTEMS.md

| Situation | Entry | Example |
|---|---|---|
| You chose between two reasonable options | **D-NNN** decision | "Use fakeredis instead of a Redis container in unit tests" |
| You changed something in DESIGN.md | **D-NNN** decision (and update DESIGN.md) | "Add `summary` block to the response" |
| A bug, failed approach, or environment issue took > 15 min or could recur | **E-NNN** error | "SQLite has no `jsonb`; mapped with a value converter to TEXT" |
| AI-generated code or advice was wrong, risky, or hallucinated | **AI-NNN** correction | "Suggested `AddStandardResilienceHandler`, whose defaults retry 3× and allow 30 s" |
| You made an assumption about the brief | Add to §3 Assumptions and DESIGN.md §3 | — |

Rules: append-only; never renumber; supersede old decisions instead of editing them (`Status: Superseded by D-0NN`); keep each entry under ~10 lines; use absolute dates (`2026-10-27`).

**Be honest in the AI Corrections Log.** It is graded evidence of how the AI was directed and verified. Include your own mistakes as an agent when the human or a test catches them.

## 6. Coding conventions

### C# / .NET (API, mocks)

- .NET 10, C# latest. `Nullable` enabled and warnings are errors (D-017) — fix the warning, do not suppress it. A `#pragma warning disable` or `!` (null-forgiving) needs a comment saying why.
- File-scoped namespaces matching folder paths; one public type per file; `sealed` by default.
- Domain values are `record` / `readonly record struct` types and immutable. Use `IReadOnlyList<T>` in public signatures.
- Use primary constructors for DI services. Register services in an `AddX(this IServiceCollection)` extension per layer (`AddApplication`, `AddInfrastructure`).
- HTTP: typed clients from `IHttpClientFactory` only; never `new HttpClient()`.
- JSON: `System.Text.Json` with a source-generated `JsonSerializerContext`; API JSON is `camelCase`.
- Errors: expected outcomes are return values (`SourceResult`, `Vin.TryParse`), not exceptions. Unexpected errors go through the global `ProblemDetails` handler.
- Logging: `ILogger<T>` with `[LoggerMessage]` source-generated methods; message templates with named placeholders (`{Source}`, `{LatencyMs}`), never string interpolation.
- Names: `PascalCase` types/members, `_camelCase` private fields, `Async` suffix on async methods, interfaces start with `I`.
- Small methods; comments explain **why**, not what. Reference decision IDs where a choice looks odd (`// no retry after attempt timeout — D-005`).
- Packages: add versions only in `Directory.Packages.props`, never in a `.csproj`.

### Blazor WebAssembly (demo client, `frontend/DocViewer.Web`, D-025)

- Same C# rules as above. The client references `DocViewer.Domain` only (for `Vin.TryParse`), never Application, Infrastructure or Api.
- Wire records live in `Api/` as small copies of the API contract, with enum values kept as wire strings. `WireContractTests` must stay green: change `docs/openapi.json` first, then the client record.
- All HTTP goes through the typed `DocumentsApiClient`; it returns `SearchOutcome` values and never throws for expected API outcomes.
- Every async view handles loading, empty, error, partial and stale states, and shows the trace id on errors.
- Mock mode (`MockApiHandler`) must serve every state the real API can return. Add a demo VIN there when you add a state.
- In a Razor attribute, an event-handler lambda (`@onchange="e => Save(…)"`) must not contain double quotes: the attribute ends at the first one. Use a constant or a helper. Explicit `@( … )` expressions with quotes inside compile fine (D5.6 review corrected an over-broad first version of this rule).
- Mock mode is picked at build time (`-p:WasmApplicationEnvironmentName=Mock`); a launch-profile environment variable has no effect (AI-011).

### Tests

- One test project per production project: `tests/DocViewer.Domain.Tests/VinTests.cs` ↔ `src/DocViewer.Domain/Vin.cs`.
- Name tests `Method_Scenario_Expected` or as a sentence: `GetDocuments_WhenServiceTimesOut_ReturnsPartialResponse`.
- Arrange / Act / Assert blocks; Shouldly assertions; `[Theory]` + `[InlineData]` for rule tables.
- No `Task.Delay`/`Thread.Sleep` to wait in unit tests: use `FakeTimeProvider.Advance`. Real delays only in WireMock-based integration tests, kept under ~3 s.
- No real external network: sources are WireMock.Net servers or fakes.
- Each invariant in SYSTEMS.md §6 has a test; tag it with `[Trait("Invariant", "4")]`.
- Do not weaken, skip or delete a failing test to get green. Fix the code, or ask the human and log a decision.

## 7. Commands

Run from the repository root. Identical on Windows, macOS and Linux.

> **This machine:** the .NET 10 SDK is now installed machine-wide (`C:\Program Files\dotnet`); new shells find `dotnet` without extra setup. A redundant per-user copy from E-004 remains in `%LOCALAPPDATA%\Microsoft\dotnet` and can be deleted.
>
> **If a build hangs with no output** (E-008), run `dotnet build-server shutdown` and retry.

| Purpose | Command |
|---|---|
| Restore local tools (`dotnet-ef`) | `dotnet tool restore` |
| Restore + build (warnings are errors; regenerates `docs/openapi.json`) | `dotnet build` |
| All tests | `dotnet test` |
| Tests + coverage gate (≥ 85 % Domain/Application; HTML report in `TestResults/coverage/report`) | `pwsh scripts/coverage.ps1` (add `-NoBuild` after a build) |
| One test project | `dotnet test tests/DocViewer.Domain.Tests` |
| Format check / fix | `dotnet format --verify-no-changes` / `dotnet format` |
| Run API (:8080) | `dotnet run --project src/DocViewer.Api` |
| Run mocks (:8081, :8082) | `dotnet run --project mocks/SalesSystem.Mock` and `dotnet run --project mocks/ServiceSystem.Mock` |
| Add EF migration (PostgreSQL, D-019) | `dotnet ef migrations add <Name> --project src/DocViewer.Infrastructure --output-dir Persistence/Migrations` |
| Run the demo UI (:5173) / in mock mode (no backend) | `dotnet run --project frontend/DocViewer.Web` / add `-p:WasmApplicationEnvironmentName=Mock` |

## 8. Boundaries — ask the human first

Stop and ask before you:

- Choose or change the language, framework, or major library (see AI-006 — this was once inferred instead of asked).
- Add a new runtime dependency or service (log a decision if approved).
- Change the API contract, a status code, or a field name.
- Change a timeout, retry, TTL, or breaker setting.
- Change or remove an invariant, or delete/skip a test.
- Commit, push, tag, create a remote repository, or rewrite git history.
- Mark a task `[x]` whose criteria you could not fully verify — say what was not verified instead.
- Do work outside the current roadmap task beyond a trivial fix.

Never: commit secrets or `.env`; log raw VINs; invent library APIs without checking documentation or the installed source; claim tests pass without running them.

## 9. Verifying AI output (for agents and humans)

The brief grades how AI output is directed and verified. Apply these checks to everything generated:

1. **Trace to requirements.** Each change maps to a ROADMAP task and, through it, to a brief requirement (DESIGN.md §2.1).
2. **Run it.** Tests, type-check, and a real request for runtime behaviour. Reading code is not verification.
3. **Check the failure paths,** not just the happy path: timeouts, malformed data, both sources down.
4. **Check library usage** against documentation for the installed version (Polly v7 vs v8 APIs, EF Core provider differences, OpenTelemetry .NET setup, and .NET 8 vs 10 OpenAPI all changed between versions — AI often mixes them).
5. **Look for silent scope creep:** extra endpoints, unused abstractions, dependencies nobody asked for.
6. **Log what was wrong** in SYSTEMS.md §4, even small things. A short honest log is worth more than a polished story.
7. **When a test fails, find out why before editing the test.** Get the full assertion output; rerun repeatedly if it might be flaky. Change the test only when the test (not the code) is wrong, and say so (AI-007).
8. **Re-measure coverage at the end of every task**, not only the task that set the bar — later changes can quietly break earlier criteria (AI-007).
9. **Check the build succeeded before trusting `dotnet test --no-build`** — a failed build silently tests stale binaries (E-002).

## 10. Session end protocol

Before you finish a session, always:

1. Update task markers in ROADMAP.md (`[~]` or `[x]`).
2. Update **Current Focus** and **Progress Summary** in ROADMAP.md.
3. Add one row to the ROADMAP.md **Session Log**: date, tasks, outcome, exact next step.
4. Add any D-/E-/AI- entries to SYSTEMS.md.
5. Report to the human: what changed, what was verified (and how), what was not verified, and what is next.
